# Same-setup baselines (comparison table)

Decided 2026-10-31: the paper's main comparison table contains **only models trained with exactly our recipe**. No official
numbers. Official checkpoints are not used, not even as initialisation. This file is the plan and the running log.
Results land in `docs/results.csv` with tag `baseline-sameSetup-<Model>`.

## Recipe (identical for every model)

Copied verbatim from `options/train/mambairv2/train_MambaIRv2_SR_x2_500k.yml` and `train_MambaIRv2_SR_x{3,4}_ft250k.yml`,
the configs MambaIRv2 and DeltaSR were trained with. Configs are generated by `tests/make_baseline_configs.py`, which
changes only `name`, `model_type`, `network_g`, the pretrain path, the test padding and the results tag.

| | ×2 | ×3 / ×4 |
|---|---|---|
| init | from scratch | this model's own ×2 500k weights (`strict_load_g: false`, x2 upsampler skipped) |
| iters | 500k | 250k |
| Adam lr / betas | 2e-4 / [0.9, 0.99] | 1e-4 / [0.9, 0.99] |
| MultiStepLR (γ 0.5) | 250k, 400k, 450k, 475k | 125k, 200k, 225k, 237.5k |
| batch (1 GPU) | 4 | 2 |
| HR crop | 128 | 192 / 256 |
| data | DF2K, hflip + rot, `num_worker_per_gpu` 4, `dataset_enlarge_ratio` 100, seed 10, L1, no warmup | same |

**Batch check (2026-10-31):** the finished ft250k runs' logs show `batch_size_per_gpu: 2` (with `gt_size` 192 / 256) for all four:
MambaIRv2 ×3/×4 (`experiments/MambaIRv2_SR_x{3,4}_ft250k/train_*_2026100*.log`) and DeltaSR ×3/×4
(`experiments/GatedMambaIR_SR_x{3,4}_lean_chgate_ft250k/train_*_20261021_233942.log`). ×2 runs used 4.

**Training crop vs window size:** an LR patch of 64 works for every model (SwinIR window 8, HAT 16, DAT split 8×32,
CAT-A axial 2/4), so no model needed 132/144 crops.

**Testing:** same test sets and metric as DeltaSR (Set5, Set14, B100, Urban100, Manga109; PSNR/SSIM on Y,
`crop_border` = scale, no self-ensemble), final checkpoint only. Each model is run on the whole image, padded the
way its official code pads (`BaselineSRModel`, `basicsr/models/baseline_sr_model.py`):

| model | test-time padding (official code) |
|---|---|
| SwinIR | flip-pad to a multiple of 8 (`main_test_swinir.py`) |
| HAT | reflect-pad to a multiple of 16 (`HATModel.pre_process`) |
| DAT | none, the arch pads internally (`DATModel`, `use_chop: False`) |
| CAT-A | flip-pad to a multiple of max(split_size_0) = 4 (`CATModel`, `use_chop: False`) |
| MambaIR | `MambaIRModel` from the official MambaIR repo (already in this repo) |
| RCAN, EDSR, SAN | none (fully convolutional / non-local). SAN's official test uses `--chop` only to save memory; we run whole images |

**Dropped (2026-10-31):** EDT and IPT. Both depend on large-scale pre-training, so they are not ported or trained.

Port notes:
- SwinIR: only added the `ARCH_REGISTRY` decorator and removed the `__main__` demo. HAT, DAT, CAT, RCAN, EDSR: unchanged.
- RCAN / EDSR / SAN work on a 0–255 range (`img_range: 255`, DIV2K RGB mean), as in their official code.
- SAN: the args object became keyword arguments. Covariance pooling computes the same centred covariance in closed form

  against the official MPNCOV (`tests/check_san_covpool.py`). SAN has 26 parameters the official forward never uses
  (`RG.*.gamma`, `conv_last`, `non_local.soca`), so its configs set `find_unused_parameters: true`.

## Log

**2026-11-01, RCAN x2 diverged.** Set14 rose to 33.52 (130k) and was 33.45 at 140k. At 143.4k l_pix jumped from ~0.01 to 1.8e2,
then 6.5e4, and Set14 fell to 9-14 dB. RCAN has no gradient clipping and works on a 0-255 range, and our lr (2e-4) is twice
RCAN's own (1e-4). Fix, recipe unchanged: the 145k-170k checkpoints went to `experiments/RCAN_SR_x2_500k/diverged_143k/`
(kept), and x2 job 1554567 was cancelled, so its resume job 1554568 restarts from the 140k state. BasicSR's resume starts the epoch's
data order from the beginning, so the batches differ from the first run. If it diverges again, ask before adding gradient clipping.

**2026-11-01, CPUs and queue.** The first 4 runs got 1 CPU each, so the 4 dataloader workers share it with training
(RCAN 0.60 s/iter vs 0.20 in the probe). The user decided to let them run. All pending training jobs got 5 CPUs:
`scontrol update JobId=X NumCPUs=5 MinCPUsNode=5`. Updating NumCPUs alone left jobs in `BadConstraints` (never start).
The 3 free GPU slots the accounts had could not be used: the only free GPUs were A100 MIG slices on speed-42, and that node is
held for higher-priority 7g.80gb jobs of other users, so only jobs shorter than about 2 h backfill there (probe jobs: 5 min
started, 1 day waited). RCAN/EDSR/SAN therefore stay queued for V100 (7-day limit). EDSR x2 moved to account `swamy`.

**2026-11-01 21:45, rebuilt chains.** A V100 freed on speed-27, but SAN 1554595 would not start, even with a 16 h limit,
while fresh probe jobs with the same request (5 CPUs, 40G, V100, up to 16 h) started at once. Jobs whose CPU count was
changed with `scontrol update NumCPUs/MinCPUsNode` after submission do not get scheduled. A fresh SAN x2 (1555956,
7-day limit) started immediately. So every pending training job (x2 / resume / x3 / x4) was resubmitted fresh with `-c 5`,
the original test jobs were re-pointed to them (`scontrol update Dependency=`), and then the old training jobs were cancelled.
RCAN's new x2 (1555960) auto-resumes from the 140k state. Lesson: set CPUs at submit time (`sbatch -c 5`), never with scontrol.
